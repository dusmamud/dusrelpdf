# dusrelpdf — Swift package

Swift Package Manager package wrapping the UniFFI-generated Swift bindings
for [dusrelpdf](https://github.com/dusmamud/dusrelpdf) — offline PDF toolkit
(merge, split, extract, remove, reorder, rotate, images-to-PDF, watermark,
page numbers, signature-image placement).

**Module:** `Dusrelpdf` — `import Dusrelpdf` (Swift 5.9+, iOS 13+, macOS 10.15+)

## Layout

```
bindings/swift/
├── Package.swift                        # manifest — see "Release toggle" below
├── build-xcframework.sh                 # macOS script that builds DusrelpdfFFI.xcframework
├── dusrelpdf_uniffi.swift               # GENERATED by UniFFI 0.28.3 — DO NOT EDIT
├── dusrelpdf_uniffiFFI.h                # GENERATED C header — DO NOT EDIT
├── dusrelpdf_uniffiFFI.modulemap        # GENERATED modulemap — DO NOT EDIT
└── Sources/
    ├── Dusrelpdf/
    │   └── dusrelpdf_uniffi.swift       # COPY of ../dusrelpdf_uniffi.swift (CI-guarded)
    └── dusrelpdf_uniffiFFI/
        ├── dusrelpdf_uniffiFFI.h        # COPY of ../dusrelpdf_uniffiFFI.h (CI-guarded)
        └── module.modulemap            # SPM form of the generated modulemap
```

Why copies? The file `scripts/regenerate-uniffi.sh` generates the Swift
sources into `bindings/swift/` (repo layout), while SwiftPM can only build
targets from files *inside* the package directory tree — so the package
keeps byte-identical copies under `Sources/`. CI
(`.github/workflows/mobile.yml`, job `swift-copies-in-sync`) fails if a
copy drifts from the generated original. After regenerating, copy the two
files again (or update the script to generate into `Sources/` directly).

## Usage

Add the package to your app's dependencies (Xcode: File → Add Package
Dependencies, or in your `Package.swift`):

```swift
dependencies: [
    .package(url: "https://github.com/dusmamud/dusrelpdf", from: "0.1.0"),
],
targets: [
    .target(name: "MyApp", dependencies: [.product(name: "Dusrelpdf", package: "dusrelpdf")]),
]
```

```swift
import Dusrelpdf

let merged = try mergePdfs(inputs: [pdfA, pdfB], options: MergeOptions())
print(try getPdfInfo(pdf: merged, common: CommonOptions()).pageCount)  // 5

let rotated = try rotatePages(pdf: pdf, options: RotateOptions(angle: 90))

do {
    _ = try extractPages(pdf: pdf, pages: [9], options: PageSetOptions())
} catch let e as DusrelError {
    print(e)  // PAGE_OUT_OF_RANGE: Page 9 is out of range ...
}
```

See `crates/dusrelpdf-uniffi/README.md` for the full API table (16
functions, records, enums, error codes in EN + HI).

## Building

```sh
cd bindings/swift
swift build            # debug
swift build -c release # release
```

No Rust toolchain is needed to *compile* the Swift module in development
mode — see the toggle below. Linking an app against the final product
needs the Rust static library (XCFramework) for the app's platforms.

### Release toggle (two-phase XCFramework flow)

`Package.swift` has a `useLocalFFI` toggle. It is `true` today because no
XCFramework has been released yet, so the package builds against a local
C target (`Sources/dusrelpdf_uniffiFFI/`, header only).

**Phase 1 — build + upload the XCFramework** (on macOS):

```sh
bash bindings/swift/build-xcframework.sh
cd bindings/swift
zip -r DusrelpdfFFI.xcframework.zip DusrelpdfFFI.xcframework
# upload the zip to the tag's GitHub Release, e.g. v0.1.0
```

**Phase 2 — wire the binary target:**

```sh
swift package compute-checksum DusrelpdfFFI.xcframework.zip
```

Paste the real download URL and the real checksum into the
`.binaryTarget(name: "dusrelpdf_uniffiFFI", ...)` in `Package.swift`, set
`useLocalFFI = false`, commit, and tag. From then on, consumers resolve
the XCFramework from the GitHub Release and need no Rust toolchain.

The URL and checksum currently in `Package.swift` are **PLACEHOLDERS**
(all-zeros checksum) — clearly marked, never valid, never to be shipped.
A checksum must be computed from the actual uploaded zip; do not invent
one.

## How the XCFramework is built

`build-xcframework.sh` does this on macOS (documented here so the release
step is reproducible by hand too):

1. **Build the Rust staticlib per slice** — `cargo rustc` with
   `--crate-type staticlib` (overrides the crate's `cdylib`+`rlib`
   declaration without touching `Cargo.toml`):
   - `aarch64-apple-ios` (iOS device)
   - `aarch64-apple-ios-sim` + `x86_64-apple-ios-sim` (iOS simulator)
   - `aarch64-apple-macos` + `x86_64-apple-macos` (macOS)
2. **Merge the pairs with `lipo`** into one fat staticlib per platform
   family:
   ```sh
   lipo -create -output libdusrelpdf_uniffi-ios-sim.a \
       target/aarch64-apple-ios-sim/release/libdusrelpdf_uniffi.a \
       target/x86_64-apple-ios-sim/release/libdusrelpdf_uniffi.a
   lipo -create -output libdusrelpdf_uniffi-macos.a \
       target/aarch64-apple-macos/release/libdusrelpdf_uniffi.a \
       target/x86_64-apple-macos/release/libdusrelpdf_uniffi.a
   ```
3. **Stage the headers** — `dusrelpdf_uniffiFFI.h` plus the generated
   modulemap renamed to `module.modulemap` (the name Xcode expects inside
   an XCFramework's Headers directory).
4. **Assemble** with `xcodebuild -create-xcframework`:
   ```sh
   xcodebuild -create-xcframework \
       -library <ios-device .a>   -headers <headers dir> \
       -library <ios-sim fat .a>  -headers <headers dir> \
       -library <macos fat .a>    -headers <headers dir> \
       -output DusrelpdfFFI.xcframework
   ```

**`BUILD_LIBRARY_FOR_DISTRIBUTION=YES`:** this XCFramework contains only
C static libraries built by cargo, so the flag has no effect on the
`xcodebuild -create-xcframework` step itself. It **is** required whenever
the Swift module is built for distribution as a prebuilt binary —
library evolution (`.swiftinterface` files). Xcode projects that archive
the Dusrelpdf Swift module for distribution must enable it (Build
Settings → Build Libraries for Distribution → YES). The bindings here
are distributed as source through SwiftPM, so the flag is not needed to
assemble this XCFramework — it is documented so a future binary-Swift
distribution step does not forget it.

## Maintenance notes

- **Regenerating bindings:** run `scripts/regenerate-uniffi.sh` from the
  repo root, then copy the regenerated `dusrelpdf_uniffi.swift` and
  `dusrelpdf_uniffiFFI.h` into `Sources/` (see layout). CI fails on drift.
- **Regeneration script caveat (integration note):** the current
  `scripts/regenerate-uniffi.sh` does `rm -rf bindings/swift` and diffs
  the whole directory, which would delete this package and fail its
  `--check`. Before the next regeneration it must be updated to
  regenerate/diff only the three generated files (`dusrelpdf_uniffi.swift`,
  `dusrelpdf_uniffiFFI.h`, `dusrelpdf_uniffiFFI.modulemap`).

## Honest limits

Same as the core (see `crates/dusrelpdf-uniffi/README.md`): no PDF
rendering, no tolerant repair of malformed PDFs, watermark / page-number
text is ASCII only, signature placement is a raster image — not a
cryptographic digital signature.
