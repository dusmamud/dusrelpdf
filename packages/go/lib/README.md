# Vendored static libraries for the Go module

`go get` installs a module from the module proxy — there is no repo
checkout, no `target/` directory and no Rust toolchain on the user's
machine. So the Go package links a **static** library vendored here,
selected per platform by the `#cgo` lines in `dusrelpdf.go`:

| Directory | Platform | File |
| --- | --- | --- |
| `lib/linux-amd64/` | Linux x86_64 (glibc) | `libdusrelpdf.a` — stored as 20 MB chunks, see below |
| `lib/linux-arm64/` | Linux aarch64 (glibc) | `libdusrelpdf.a` — stored as 20 MB chunks, see below |
| `lib/darwin-arm64/` | macOS Apple Silicon | `libdusrelpdf.a` — **not vendored yet** |
| `lib/darwin-amd64/` | macOS Intel | `libdusrelpdf.a` — **not vendored yet** |
| `lib/windows-amd64/` | Windows x86_64 (MinGW/GNU) | `libdusrelpdf.a` |

Only the platforms with a file present build. macOS and Windows
libraries are built by `.github/workflows/release-assets.yml`
(manual dispatch) and vendored by a maintainer from its artifacts —
this VM cannot build them. Until a platform's archive is vendored,
building the Go package on that platform fails at link time with a
missing-file error; that is honest, not silent.

The matching header is vendored alongside the package, not here:
`packages/go/dusrelpdf.h` is a verbatim copy of
`crates/dusrelpdf-ffi/dusrelpdf.h` (generated by cbindgen). The
`#cgo CFLAGS: -I${SRCDIR}` line makes cgo read the vendored copy.

## Why the Linux archives are stored as chunks

A Rust static library is ~55 MB, and the GitHub Git Data API
(the push path this repo uses) rejects blobs over ~40 MB (measured
2026-11-13: 40 MB OK, 45 MB fails with HTTP 422). Plain `git push`
is not available here either (no raw credential on the machine).
So the two Linux archives are committed as 20 MB parts
(`libdusrelpdf.a.part00`, `.part01`, `.part02`) and reassembled by
`assemble.sh` (in this directory). Windows fits whole at 40 MB and
is stored as one file.

- **Users:** after `go get`, run `go generate ./...` once in the
  module (or `sh lib/assemble.sh`). It concatenates the parts and
  verifies the SHA-256 in `SHA256SUMS` — a mismatch fails loudly.
  No Rust toolchain and no network needed; the parts are already in
  the module. CI runs the same step before `go test`.
- **Maintainers (re-vendoring):** rebuild the `.a`, then split it
  and refresh the checksum:
  ```sh
  split -b 20M -d libdusrelpdf.a libdusrelpdf.a.part
  sha256sum libdusrelpdf.a >> SHA256SUMS  # keep the file sorted by path
  rm libdusrelpdf.a   # the assembled file is gitignored, never commit it
  ```
  Never commit the assembled `.a` for linux-amd64/linux-arm64 —
  it is gitignored and excluded from the API push script.
- **Shrinking does not work:** `strip` (plain) deletes the archive
  symbol table and makes the `.a` unlinkable; `strip --strip-debug`
  saves nothing (a release build has no debug info); LTO builds
  are *larger* (~101 MB). The chunk split is the fix, not a
  workaround for a build flag.

## How a library is built

Every archive is built from `crates/dusrelpdf-ffi` with the
`staticlib` crate-type (see its `Cargo.toml`) — the cdylib alone
cannot be statically linked:

```sh
# Linux x86_64 (from the repo root)
cargo build -p dusrelpdf-ffi --release
cp target/release/libdusrelpdf.a packages/go/lib/linux-amd64/
# A static Rust archive is large (~57 MB: every dependency object
# file is kept, the final binary only links what it uses).
# Do NOT strip it: plain `strip` deletes the archive symbol table
# and makes the `.a` unlinkable, and `strip --strip-debug` saves
# nothing (a release build has no debug info). Split it into 20 MB
# chunks instead — see "Why the Linux archives are stored as chunks"
# above.

# Linux aarch64 (needs the target + a cross linker)
rustup target add aarch64-unknown-linux-gnu
sudo apt-get install gcc-aarch64-linux-gnu
CARGO_TARGET_AARCH64_UNKNOWN_LINUX_GNU_LINKER=aarch64-linux-gnu-gcc \
  cargo build -p dusrelpdf-ffi --release --target aarch64-unknown-linux-gnu
cp target/aarch64-unknown-linux-gnu/release/libdusrelpdf.a \
  packages/go/lib/linux-arm64/
# (Do NOT strip the archive — see "Why the Linux archives are
# stored as chunks" above. Split the Linux archives into 20 MB parts
# instead; the Windows archive fits whole.)

# Windows x86_64, GNU staticlib (what MinGW cgo links — NOT the MSVC
# .lib, which MinGW cannot use)
rustup target add x86_64-pc-windows-gnu
sudo apt-get install gcc-mingw-w64-x86-64
CARGO_TARGET_X86_64_PC_WINDOWS_GNU_LINKER=x86_64-w64-mingw32-gcc \
  cargo build -p dusrelpdf-ffi --release --target x86_64-pc-windows-gnu
cp target/x86_64-pc-windows-gnu/release/libdusrelpdf.a \
  packages/go/lib/windows-amd64/
# (Do NOT strip the archive — see above.)
```

`.a` via `lipo`, built on a macOS runner).

## Keep the vendored files in sync

- **After any change to the exported C API** (`crates/dusrelpdf-ffi/src/lib.rs`):
  regenerate the header and refresh the copy:
  ```sh
  cbindgen --config crates/dusrelpdf-ffi/cbindgen.toml \
    --crate dusrelpdf-ffi \
    --output crates/dusrelpdf-ffi/dusrelpdf.h
  cp crates/dusrelpdf-ffi/dusrelpdf.h packages/go/dusrelpdf.h
  ```
  then rebuild and re-vendor **every** platform library — a stale
  `.a` silently keeps old behaviour. The release-assets workflow has
  a header-drift check that fails if the two copies differ.
- **Do not edit `dusrelpdf.h` or a `.a` by hand.** They are build
  outputs, committed only so `go get` works without Rust.
- **Versioning:** the vendored libraries are whatever commit they
  were built from. When the Go module is tagged (`packages/go/vX.Y.Z`),
  the tag must be cut from a commit whose vendored libraries were
  rebuilt from that same commit's Rust source — never tag a commit
  with stale libraries.
- **Binary size:** each `.a` is a full static Rust build (~57 MB:
  every dependency object file is kept in the archive, the final
  binary only links what it uses). That is the price of a
  self-contained module; the alternative (users building the library
  themselves) is documented in `packages/go/README.md` under
  "Build the library yourself".

## Why static, not shared?

A vendored `.so`/`.dylib`/`.dll` would need to be found at runtime
(`LD_LIBRARY_PATH`, rpath, or sitting next to the binary) — fragile
for a library. A static `.a` is linked into the user's binary once,
at build time, and then there is nothing else to ship. The system
libraries the static Rust library needs (`-ldl -lpthread -lm` on
Linux, CoreFoundation/Security on macOS, ws2_32/userenv/bcrypt/ntdll
on Windows) are listed in the `#cgo` lines in `dusrelpdf.go`.
